# MPE input paths (clap-wrapper 4585bc6, 2026-10-28)
Evidence tags: [code] = file:line in repo; [web] = web search (thin, KVR forum / Ableton manual); [knowledge] = spec/background, unverified here.

## 1. Plugin today [code]
- plugin/src/GigaGrainsPlugin.cpp:2228-2237: one input note port, supported = CLAP|MIDI|MIDI_MPE, preferred = CLAP. No output note port (2225).
- Handles CLAP_EVENT_NOTE_ON/OFF/CHOKE (925-980; note_id slots for note-off by id, R15) and CLAP_EVENT_MIDI note on/off, vel0 = off, CC123 (981+).
- Controls only: CC1, channel pressure (D0), pitch bend (E0) -> ControlEvent (873-915), carrying a channel but treated as global transport-style controls (mod matrix sources).
- No handling of CLAP_EVENT_NOTE_EXPRESSION, no per-note param events, no CC64 sustain, no CC74, no poly pressure (A0). grep for NOTE_EXPRESSION / MODULATABLE_PER_NOTE / CLAP_PLUGIN_AS_VST3 in plugin/ core/ clients/: none (core/src/ParamIds.cpp:20 only IS_MODULATABLE).
- Plugin does not expose clap_plugin_as_vst3, so wrapper defaults apply (see 2).

## 2. VST3 wrapper [code, src/wrapasvst3.cpp, detail/vst3/process.cpp]
- Note on/off -> CLAP_EVENT_NOTE_ON/OFF with channel, note_id, key, velocity (process.cpp:520-575). Off carries release velocity. Note-id kept in _activeNotes until plugin sends NOTE_END/CHOKE (process.cpp ~800-830, removeFromActiveNotes) -> plugin should emit NOTE_END when a voice finishes or the table grows.
- Note expressions: wrapper only advertises types in _expressionmap. Default (wrapasvst3.h:603-607) is PRESSURE alone unless built with CLAP_SUPPORTS_ALL_NOTE_EXPRESSIONS (CMake option, default OFF, CMakeLists.txt:104), OR the plugin returns a bitmask from the clap_plugin_as_vst3 extension (include/clapwrapper/vst3.h:137-163; read at wrapasvst3.cpp:1239-1246). The per-plugin extension overrides the compile default. Types: Volume, Pan, Tuning, Vibrato, Expression, Brightness, Pressure.
  - Caveat: wrapasvst3.cpp:1466-1496 registers Volume/Pan/Tuning/Vibrato/Expression/Brightness with INoteExpressionController; PRESSURE is NOT registered ("handled by IMidiMapping -> Polypressure", 1497), so Live/Cubase see no pressure note expression type.
- Conversions: kNoteExpressionValueEvent -> CLAP_EVENT_NOTE_EXPRESSION, looked up via note_id in _activeNotes; unknown typeId dropped (process.cpp ~620-690). Tuning: (v-0.5)*2*120 => semitones in +-120 (VST3 range is mapped to whole +-120 st; the host decides the real scale, Cubase uses 0..1 over +-120? [knowledge] verify with a test). Note-on tuning offset also converted when tuning supported (process.cpp:546-565).
- kPolyPressureEvent: if _supportsPolyPressure(=PRESSURE bit) -> NOTE_EXPRESSION PRESSURE; else raw MIDI A0.
- MIDI CCs/bend/channel pressure: IMidiMapping is created only if some note port supports DIALECT_MIDI (checkMIDIDialectSupport, wrapasvst3.cpp:1239,1247-1262). We do. For each of _numMidiChannels (default 16, wrapasvst3.h:551; override via getNumMIDIChannels) and every VST3 controller number (kCountCtrlNumber = 130 incl. bend 129, aftertouch 128) a hidden parameter is created (wrapasvst3.cpp:1393-1440, ids from 0xb00000), and getMidiControllerAssignment (871-886) returns it for bus 0. Param changes become CLAP_EVENT_MIDI 3-byte messages (process.cpp ~318-360): pitch bend E0|ch, CC B0|ch, channel pressure D0|ch, program change C0|ch. This is dialect-independent: raw MIDI even though preferred dialect is CLAP.
  - Lossy: only the LAST point of each parameter per block is used (process.cpp ~300: getPoint(nums-1)). Pitch-bend/pressure sub-block resolution is lost; cost for MPE is smoothing only at block rate.
  - Ordering: MIDI-from-param events and note events share one queue sorted by time (stable) (sortEventIndices, process.cpp ~440), so a bend with the same sample offset as a note-on follows it by append order: note events are appended first (processInputEvents before parameter changes). A bend that precedes the note-on at the same offset can arrive AFTER note-on. Plan: apply the channel's latest bend at note-on is not enough; must also apply it when it arrives after.
  - MIDI channel on a CLAP note-on from VST3 comes from noteOn.channel. Whether Live/Bitwig fill it with the MPE member channel for VST3 [unverified]; the IMidiMapping CC74 etc. go by param channel.
- Output: NOTE_EXPRESSION, PARAM_MOD, MIDI out events are swallowed (return true, nothing sent).
- Live's MPE for VST3 [web: Ableton manual "Editing MPE" confirms Live has an "MPE Mode" per plug-in device and can modulate MPE data for MPE-enabled plug-ins; nothing on the VST3 mechanism]. [knowledge, unverified] Live 12 sends VST3 MPE as note expressions (Tuning, Volume/Pan/Brightness types, per noteId) only if the plugin exposes INoteExpressionController types; otherwise falls back to channelized MIDI (member channels in noteOn.channel plus IMidiMapping parameters). So for Live VST3: expose Tuning + Brightness(CC74 slide) + Pressure through clap_plugin_as_vst3 (supportedNoteExpressions = TUNING|VOLUME|PAN|BRIGHTNESS|EXPRESSION|VIBRATO) and ALSO handle MIDI MPE. Pressure is not advertised by wrapper (see above): rely on IMidiMapping channel pressure (D0) per channel with member-channel -> note mapping. Needs a real test in Live (cannot be verified from code).

## 3. AUv2 wrapper [code, src/wrapasauv2.cpp, detail/auv2/*]
- No kAudioUnitProperty_SupportsMPE anywhere (grep across src/, include/, docs/): not implemented. [knowledge] Live and Logic gate MPE on that property (AU MPE support landed in macOS 10.15 / Logic 10.5; Logic sends per-channel MPE only to AU instruments that report SupportsMPE; Live AU MPE Mode likewise). Without it, Logic routes MPE controllers as single-channel MIDI; Live sends channel-1 only or plain channelized MIDI [unverified]. Conclusion: MPE over AU needs a wrapper patch (carry-over row) or is blocked.
- MIDI in: MIDIEvent (auv2_base_classes.h:440-457) and MIDIEventList/UMP (467-525) -> ProcessAdapter::addMIDIEvent (process.cpp:513-683). StartNote/StopNote (auv2_base_classes.h:556-581, process.cpp:736) get an internal note_id, channel from group id.
- Dialect handling: _preferred_midi_dialect = chooseInputDialect(preferred, supported) (process.cpp:63; detail/shared/midi_translation.h:35). With our CLAP preference:
  - note on/off -> CLAP_EVENT_NOTE_ON/OFF, note_id = -1 (process.cpp:548-562), channel kept.
  - A0 poly pressure -> NOTE_EXPRESSION PRESSURE note_id -1 key+channel (591-608).
  - D0 -> channel-wide PRESSURE expr (key -1) (619-633).
  - E0 pitch bend -> channel-wide TUNING expr with a HARD-CODED +-2 semitones (643-658): wrong for MPE member channels (48) and the plugin cannot recover the raw 14-bit value or know the range.
  - CC (B0), program change -> raw CLAP_EVENT_MIDI (CC74, CC64, CC1 arrive as MIDI even in CLAP dialect).
  If the plugin prefers DIALECT_MIDI (or MIDI_MPE), everything including bend arrives as raw MIDI (process.cpp:563-575, 609-615...). Consequence: the preferred dialect changes what AU delivers; today our CLAP preference means the AU bend is a +-2 st tuning expression that the plugin ignores (only CLAP_EVENT_MIDI E0 is handled).
- Also a UMP (MIDI 2.0) path exists (AUMIDIEventList) with note ids; not examined deeply.

## 4. Bitwig -> CLAP [web only, KVR forum posts; not official]
- Bitwig converts MPE into note expressions for CLAP plugins; for CLAP it does NOT convert back to MIDI MPE; "no MPE switch for CLAP plugins; automatic". [web]
- [knowledge] A CLAP plugin that prefers DIALECT_CLAP (and supports it) gets NOTE_ON/OFF with note_id and CLAP_EVENT_NOTE_EXPRESSION (TUNING in semitones, already scaled by bend range, per note_id; PRESSURE 0-1; BRIGHTNESS = CC74 0-1; VOLUME 0-4; PAN 0-1; VIBRATO; EXPRESSION). A plugin that prefers MIDI_MPE gets channelized MIDI [unverified in Bitwig]. No evidence found of Bitwig sending MCM (RPN 6) or RPN 0 to a plugin; the CLAP note expression path makes it unnecessary. Test with the shipped build in Bitwig.
- Bitwig's per-note expression tuning in note events is already in semitones with bend range applied; do not apply an MPE range yourself on the CLAP path.

## 5. MPE spec and LinnStrument [knowledge, not verified here]
- MPE spec (MMA/AMEI RP-053): Configuration Message = RPN 6 (CC101=0, CC100=6, CC6=member channel count) on the manager channel (1 = lower zone, 16 = upper). Member channels default bend range +-48 semitones, master channel +-2. Per-channel RPN 0 changes it. Members: bend (E0), CC74 timbre, channel pressure D0 (per-note), CC64 sustain etc. on the master.
- LinnStrument in MPE mode sends MCM at connect/mode switch, bend range default 24 (hardware setting; LinnStrument's own default is 24 st, configurable; Linn sends RPN 0 on connect), uses channels 2-16 rotating, CC74 slide, channel pressure, note-off with release velocity (optional). Hosts typically do NOT forward MCM to plugins. So a plugin must default the member bend range to +-48 per spec and let the user change it; accept RPN 0 / RPN 6 when present (via CLAP_EVENT_MIDI CCs 101/100/6/38).
- Only the MIDI path needs bend range knowledge. Note expression paths (CLAP/VST3 tuning, Live note expression) carry final semitones.

## 6. Per-note parameter modulation [code]
- CLAP_PARAM_IS_MODULATABLE_PER_NOTE_ID etc.: not used by plugin. Wrapper VST3 sets note_id=-1, channel -1, key -1 on all incoming parameter changes ("nothing note specific", process.cpp ~385-390), outputs PARAM_MOD ignored (process.cpp ~620). So per-note param mod is CLAP-only (Bitwig) and has no VST3/AU mapping. Voices must be built so per-note modulation could be added later (Bitwig polyphonic modulators send PARAM_MOD with note_id).

## Recommendation for sub-project 1
Must implement, one voice model fed by three adapters:
1. CLAP path (Bitwig CLAP): NOTE_ON with note_id; NOTE_EXPRESSION for TUNING (st), PRESSURE, BRIGHTNESS, VOLUME, PAN, keyed by note_id (fallback channel+key); NOTE_OFF release velocity; emit NOTE_END via the output events when a voice finishes (also needed by VST3 wrapper's active-note table). Add CLAP note-port output? Not needed.
2. MIDI-MPE path (Bitwig VST3, Live VST3 fallback, Live AU/Logic raw): channelized MIDI: E0 per member channel bend (default +-48, RPN 0 override, global channel +-2), CC74, D0 channel pressure, A0 poly pressure, CC64 sustain (global, master channel or all channels), CC1, CC123/120, release velocity from 0x80. Apply a channel's stored bend/pressure/slide at note-on; per-channel state keyed by channel; zone config via RPN 6 optionally; if no MCM seen, treat channels 2-16 as members when more than one channel is active? Decide rule explicitly in design.
3. VST3 note expressions: implement clap_plugin_as_vst3 returning TUNING|VOLUME|PAN|BRIGHTNESS|EXPRESSION|VIBRATO (the wrapper's own PRESSURE is inert) and getNumMIDIChannels = 16; the host then may send per-noteId expressions that the wrapper maps to CLAP_EVENT_NOTE_EXPRESSION: same adapter as path 1.
Consider preferring DIALECT_MIDI? Trade-off: With preferred CLAP the AUv2 wrapper converts bend into a +-2 st tuning expression (wrong for MPE) so AU MPE over CLAP dialect is unusable; with preferred MIDI_MPE/MIDI, the AU path is raw MIDI (good) but Bitwig CLAP presumably switches to MIDI MPE/MIDI instead of note expressions [unverified], and the VST3 note path is unaffected. Need a Bitwig test. Option: keep CLAP preferred and accept AU limitation as carry-over; or ship a dialect switch.
Blocked by wrapper (carry-over rows): (a) AUv2 has no kAudioUnitProperty_SupportsMPE, so Live AU / Logic won't send per-note MPE; fix = wrapper patch; (b) AU bend under CLAP dialect hard-coded +-2 st and note_id -1; (c) VST3 channel-state parameters are last-point-per-block; (d) VST3 PRESSURE note expression is not registered; (e) no per-note param mod in VST3/AU; (f) CLAP_SUPPORTS_ALL_NOTE_EXPRESSIONS off by default unless the as_vst3 extension is implemented; (g) Live VST3 MPE delivery mode cannot be confirmed from code or docs, needs a host test.
