# M3 Scenes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eight scenes inside one instance, each a captured set of base parameter values. A scene is recalled at once, over a glide or on the transport's next line, from a host parameter, a MIDI Program Change or the editor. Two scenes morph with one control, and a punch jumps to Scene B and back. With the bank empty and the seven controls at rest, nothing moves.

**Architecture:** A pure, allocation-free bank (`core/Scenes.h`) holds eight `Scene`s: values plus a per-slot mask. The plugin's inactive path and the `Processor` share its functions. The `Processor` acts on scenes only at control-grid boundaries, inside `commitPending`, in NB1's order. Every scene action writes base values as a committed host event would, so ramps, latching, Freeze arming and Mode switches follow unchanged. The written slots are reported, and the plugin sends them to the host as `PARAM_VALUE` out-events. The bank is saved as a `<scenes>` element in `PTCH` with no version bump. On the audio thread the `Processor` writes it (store, clear) and publishes it back with an epoch. Loads reach the audio thread inside `loadedState_`.

**Tech Stack:** C++23, CLAP 1.x, clap-wrapper, Catch2, CMake presets, `gg-render` goldens.

**Spec:** `docs/superpowers/specs/2026-11-07-m3-scenes-design.md` (N1–N15, NB1–NB16; parent `docs/superpowers/specs/2026-11-07-m3-program-design.md`). File and line references are at `243a44a` (this branch's base, `m3-voice` at `18ac47d`).

## Plan decisions (Claude's, made without the director at his request; NP1…)

- **NP1.** `isSceneSlot` is not `constexpr`. The first call builds a static `SceneSlotSet` from `paramMeta(slot, Mode::Fx)`'s `CLAP_PARAM_IS_AUTOMATABLE` flag, minus Budget and `isSceneControl`; a test pins that both products' flags agree. Scenes.cpp's per-slot morph table (stepped flag, min, max) is built the same way, once. `warmSceneTables()` builds both off the audio thread. The `Processor` constructor and the plugin constructor call it.
- **NP2.** The FX view's Scenes panel lands in Task 1, beside the parameters, because `EditLayout`'s "every parameter has exactly one placement" fails without it. The remote page lands with the plugin surface (Task 8).
- **NP3.** Scene commands are `CommandEvent`s of three new `CommandKind`s (`value` = k, `layer` ignored). Inside the `Processor` they go to their own group array, `pendingSceneCommands_`, capped at `kMaxGroupSceneCommands = 3 * kScenes`. They never take a ring command's place under `kMaxGroupCommands`, and `applyCommands` never sees them. `validCommand` admits them when `value` is an integer from 1 to 8 (`value == std::floor(value)`).
- **NP4.** In the event loop, a Program Change of program p (0 to 7) writes `pendingBase_[Scene] = p + 1` and sets `pendingSceneForced_`. A later Scene base event in the merged order clears the flag. So of a Scene event and a Program Change in one group the later wins (NB1), with no extra ordering.
- **NP5.** A morph change writes only when `A_eff` is filled and the new Scene B is filled (N5, literally). Moving Scene B to None therefore writes nothing: the values stay where the morph left them.
- **NP6.** A recall of an empty scene writes nothing and leaves `A_eff` as it was.
- **NP7.** `setBases(values)` sets `A_eff` to `sceneIndexOf(values[Scene])` and drops the waiting recall, the glide and the punch. The FX's `loadedState_` path and the instrument's offer path both call `setBases`, so both set `A_eff` (NB2).
- **NP8.** `fromStateXml` forces Scene Punch and Scene Store to 0 on every load (`clearSceneMomentaries`). `readPreset` applies `dropRingParams` to the bank it returns. So every load path, the plugin's and `gg-render`'s, gets both rules without remembering to call them. `toStateXml` writes the values as given.
- **NP9.** `Processor::takeSceneWrites()` returns the slots reported since the last take (written by a scene action or by a Program Change, and changed bit for bit), minus every slot with a pending base event, and clears the set. The set persists across `setBase`, so a flush's immediate action is reported too.
- **NP10.** `uiSceneCommand` while inactive acts on the main thread: `capture` into `scenes_` from `values_`, a clear, or `recallInto` on `values_`. A recall then asks the host to rescan values (`clap_host_params.rescan(CLAP_PARAM_RESCAN_VALUES)`). Every one marks the state dirty. While active it is queued on `commandQueue_` as the ring commands are.
- **NP11.** Whole-state undo entries skip the seven: `EditorPlugin::pushWholeState` copies `vBefore`'s seven into the after values before `pushSnapshot`, so they never differ.
- **NP12.** The on/off controls (Punch, Store) are on at `>= 0.5f` (NB9, as `layerModeOf` reads Mode). Freeze's `> 0.5f` stays as it is.
- **NP13.** The recall's cost is measured by a hidden Catch2 case, `[.scenes-cost]`, run by hand from the `release` tree. It is recorded in the carry-over row and the gate's commit, and asserts nothing about time.
- **NP14.** The tempo seam (§4.4): sub-project 7 has no spec or code on any branch as of `243a44a`. So Task 6 adds `TransportSource::beatPosition()`, `beatsPerBar()` and `hasBeats()`. Before Task 6 starts, `git log m3-sp7-temposync` is checked. If sub-project 7 has merged a beat-position accessor into `m3-voice`, Task 6 uses it and adds only what it lacks.

## Review Focus

1. **A host sends a CLAP param-mod event on Scene Morph (or any of the seven):** it is ignored, and no base is written (N13). Task 4's `scenes_mod_event_on_control_ignored`.
2. **A state loads while the punch pad is held, and the host sends Punch Off after it:** the load forced Punch Off and dropped the return set, so the release writes nothing and the loaded values stand. Task 5's `scenes_punch_release_after_load_writes_nothing`.
3. **Scene k is cleared while a quantized recall of k waits:** the recall fires on its line, finds k empty, writes nothing, and `A_eff` keeps its scene (NP6). Task 6's `scenes_clear_while_waiting`.
4. **Store fires during a glide toward the same scene:** it captures the bases as they stand mid-glide, and the glide runs on to its latched targets. Task 5's `scenes_store_during_glide_captures_current`.
5. **The host's out-event list refuses pushes, or is null (a flush with no `out`), across many calls:** the plugin keeps the pending set and never crashes. The next call that pushes sends each slot's latest `values_` once. Task 8's `plugin_scene_report_null_out`.
